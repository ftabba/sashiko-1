# ARM64 Hyp (EL2): maintainer notes

These notes cover review priorities and house-style conventions for the ARM64 hypervisor code running at EL2 (nVHE and pKVM).

- Judge pKVM findings against its threat model. Breaking guest confidentiality or integrity against the host, hypervisor integrity against host or guests, or host availability against guests is a bug. Anything outside that model is not.
- Host availability against itself is out of scope. If the host kernel can panic itself, or trigger a hyp panic from its own privileged code paths, that is not a bug. Report it as a hardening improvement, and only when the fix is cheap.
- Misbehaving firmware or hardware (EL3, SMMU, GIC) is beyond the trust boundary. Do not report EL2 panics caused by such faults as bugs.
- A hyp panic that a guest can trigger (through DMA, hypercall side effects or shared memory) is a bug.
- A hyp panic that host userspace can trigger (through a syscall or ioctl that leads to a hypercall) is a bug, because it breaks the Linux rule that userspace must not crash the kernel.
- Reachability of a fatal path is checked, not assumed. List every writer of the value the fatal path reads: host userspace through an ioctl, the guest (including guest state that EL2 copies out to the host and reads back on a later entry), firmware or hardware, and the host kernel alone. The path is host-kernel-only, and so a hardening improvement rather than a bug, only when neither userspace nor the guest can put a bad value there.
- Treat two questions about an EL2 assertion separately. Correctness asks whether the assertion is the right kind of check. Severity asks whether triggering it is a bug. If a WARN_ON should be an error return but only the host kernel can reach it, it is a hardening improvement. If a guest or host userspace can reach it, it is a bug.
- If an EL2-internal invariant can be broken because of a bug elsewhere, report that other bug. Do not demote the local WARN_ON that defends the invariant.
- Do not use CONFIG_BUG=n (an EXPERT-only opt-out) as grounds to escalate a defensive WARN_ON into a NULL-dereference finding.
- BUG() is the house style in arch/arm64/kvm/hyp/nvhe/. Do not flag swapping BUG() for hyp_panic() (or the reverse) as a regression.
- A redundant kern_hyp_va() on a pointer it leaves unchanged deserves at most a cleanup note, not a bug report. The cleanup is still worth suggesting, because a redundant call hides the host-to-EL2 boundary that each kern_hyp_va() call site marks.
- In nVHE and pKVM, a hypercall or trap handler at EL2 runs to completion on the trapping CPU with interrupts masked: there is no scheduler, no preemption and no deferred work at EL2. Do not report a race that depends on one handler being interrupted, or its tail deferred, on the same CPU. Concurrency between two CPUs each running a handler against shared EL2 state is real, and is judged under the kernel memory model as usual.
- For a protected vCPU, what the hypervisor takes into HCR_EL2 from the host's value is an allowlist, and a review of a change to it sorts each bit the patch touches into one of two classes. Configuration bits define the guest's translation, execution state, interrupt routing and feature traps, and the host must not be able to set or clear them. Host-owned runtime signals are a policy or an event the host applies at runtime and that is meaningless unless it reaches the vCPU that runs, such as the WFI/WFE trap policy and virtual SError injection. The allowlist must carry them in, and a signal the guest consumes (the PE clears VSE when the guest takes the virtual SError) must reach the host again. Virtual IRQ and FIQ pending stay out, because a protected guest's interrupts arrive through the vGIC.
- In the protected-vCPU HCR_EL2 allowlist, over-inclusion and under-inclusion are both bugs: a configuration bit taken from the host lets the host change the guest's environment, and a host-owned signal left out means the host can no longer apply that policy or deliver that event. Copying only the allowlisted signals is correct, not a partial sync.
- Whether vCPU state belongs to vCPU load or to every guest entry is decided by its requirement, not by where the code puts it today. State the host changes between entries (a pending virtual SError, a WFI/WFE policy change) belongs on the per-entry path. State fixed for the life of the load (the fine-grained trap configuration of a non-protected guest) belongs at load. Report state at the wrong cadence. Do not report per-load state as missing from the per-entry path when its requirement places it at load.
- Whether EL2 saves the host's FP/SIMD state before loading a guest's differs between nVHE and pKVM, and the gate has moved between kernel versions. Read the gate at the commit under review before reporting the save as missing where the host's own lazy FP machinery covers it, or as wasted where pKVM saves eagerly for a non-protected guest.
